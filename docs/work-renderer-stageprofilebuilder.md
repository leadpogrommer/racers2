# Renderer stage-profile builder

`RendererTextureStageManager::BuildProfileStagePlan` reconstructs the profile dispatch at retail `0x004e4fd0`. The function is `thiscall`, takes a `RendererStagePlanRequest*` followed by an unused DWORD, returns the resolver result, and cleans both stack arguments (`ret 8`). The request's first defaults DWORD at `+0x14` selects the profile and is also the subrecord-group cache key. The owning manager is the renderer member at `DisplayRenderer::m_textureStageManager`.

The recovered cases are `0x03`, `0x11`, `0x21`, `0x101`, `0x201`, and `0x205`. Unknown profile values, including `0x09`, return zero without creating a group. Profiles `0x03`, `0x11`, `0x21`, and `0x101` append two or three fixed groups of four-DWORD descriptors, then initialize the group's profile-index fields and call the existing apply adapter. The `0x201` and supported `0x205` cases also allocate and link one manager stage record. The record's final selector is `2` when the renderer lacks cube-texture support and `3` when it has it. Profile `0x205` requires the shared-memory multitexture capability; otherwise retail falls through to the profile-`0x03` construction while retaining the request's original cache key.

The descriptor words and group mutations are transcribed from the writes in `data/retail-disasm.txt` and cross-checked against `data/ghidra-export/004e4fd0.c`. `AddTextureStageSubrecords`, `SetTextureStageProfileValue`, `InitializeAndLinkTextureStageRecord`, `DisplayRenderer::SupportsCubeTextures`, `DisplayRenderer::SupportsSharedMemoryMultitexturing`, and the stage-plan apply adapter carry the detailed operations. The latter adapter represents retail `0x004e5f30` and is owned by the stage-plan resolver work.

Retail lazily fills static descriptor globals behind bit flags and registers several one-instruction `ret` callbacks with `atexit`. Those descriptor addresses are only consumed by the copying helper in this function; the linked nodes do not retain the source pointers. This implementation therefore uses equivalent constant descriptor arrays and omits the no-op callback registrations. The profile inputs and emitted manager/group records are preserved; the internal CRT registration side effect is not reproduced. This structural simplification, together with the many descriptor-driven paths, keeps the function `STUB` pending isolated raw comparison and reviewer validation.

The direct raw evidence for the extent is `0x004e4fd0` through the `ret 8` at `0x004e5d82..0x004e5d84`, totaling 3,509 bytes. The call sequence loads the opaque DWORD into EDX and the request into EAX, then pushes EDX followed by EAX before CALL; thus the request is the first callee argument. The body consumes the request and ignores the second argument.

The isolated VC6 build linked successfully. Raw similarity is 9.93%; the function remains STUB. No game runtime check was performed.
